## 5. 功能目标

- 让主选项、次结果和承载落位真正影响下一轮战斗结果与原因说明
- 强化五线承载的玩家可感知性，而不是只做槽位展示
- 让养成完成后玩家能明确知道“本轮改了什么、下一轮怎么生效”
- 不追求：
  - 局外养成
  - 多层级稀有度系统
  - 多职业通用大改

## 8. 模块拆分

- 模块名称：养成选择结果承载扩展
  - 模块类型：Mode Data
  - 模块职责：明确记录主结果、次结果、承载落点、覆盖前内容与下一轮准备状态
  - 关系：服务端写入，客户端只消费
  - 是否新增：扩展现有 `BattleModeData`
- 模块名称：五线承载战斗生效扩展
  - 模块类型：Mode Logic
  - 模块职责：把五线承载影响映射进下一轮战斗结果与原因解释
  - 关系：依赖 `BattleA2ContentCatalog`、`BattleBContentCatalog`
  - 是否新增：扩展现有逻辑，不新起平行战斗系统
- 模块名称：承载变化展示扩展
  - 模块类型：Controller / UI
  - 模块职责：在玩家选择后明确显示“落到哪条线、落到哪个承载位、替换了什么”
  - 关系：扩展 `BattleA2PanelController`
  - 是否新增：否

## 9. 数据流与状态流

- `Config`
  - 沿用现有 hero / cultivation 内容池，不单独新起配置体系
- `Data`
  - 扩展承载变化的表达字段：
    - 本轮主结果落点
    - 本轮次结果落点
    - 被替换承载内容
    - 下一轮准备状态摘要
  - 保持 `buildProfile` 为单主角承载权威状态
- `Logic`
  - 服务端在养成确认时同时完成：
    - 承载写入
    - 覆盖旧承载判断
    - 下一轮战斗的承载影响准备
    - 可读摘要生成
  - 下一轮战斗结果与 C1 结果摘要联动，指出承载变化来源
- `UI`
  - 养成阶段展示主结果 / 次结果落位
  - 展示空位、已承载、被替换三类状态区别
  - 提供下一轮准备状态摘要

## 10. Client / Server 责任分配

- 客户端负责：
  - 展示承载变化与下一轮准备状态
  - 不在本地推导承载覆盖结果
- 服务端负责：
  - 权威决定主结果 / 次结果写入哪个承载位
  - 计算覆盖旧承载与下一轮战斗影响
  - 广播更新后的 battle 快照
- 需要同步的状态：
  - 承载位内容
  - 主结果 / 次结果落点
  - 被替换承载摘要
  - 下一轮准备状态摘要
- 同步方式：
  - 扩展现有 `NetworkSyncBattleStateRpc`

## 11. 关键流程

1. 进入 `Cultivation`
2. 服务端生成 4 个主选项与次结果
3. 玩家提交选择
4. 服务端权威决定：
   - 主结果落位
   - 次结果落位
   - 是否覆盖旧承载
   - 下一轮准备状态摘要
5. battle 快照同步给客户端
6. 客户端立即更新承载状态展示
7. 下一轮 `Battle` / `BattleResult` 中读取承载变化，并在结果原因里体现

### 异常与回退流程

- 若目标承载位为空：
  - 直接写入并明确显示“新承载”
- 若目标承载位已有内容：
  - 明确显示“被替换内容”
  - 不允许无提示覆盖
- 若某条线当前未成型：
  - 明确展示空位状态

## 13. 进入条件、完成出口与回退策略

- 进入实现前条件：
  - A6/A7 与 B2/B3 已有基础原型
  - 当前 `buildProfile` 与五线承载字段已存在
- 最小完成出口：
  - 玩家选完养成后，能明确知道选到了哪条线、落到哪个承载位
  - 下一轮战斗结果能明确指出至少一种承载变化带来的影响
  - 空位、已承载、被替换三类状态可区分
- 回退策略：
  - 若“承载变化 -> 战斗反馈”映射过大，首版优先做 3 类最小映射，不一次性铺满全部分支

## 15. 风险与待确认项

- 风险点：当前战斗仍以总分聚合为主
  - 影响：承载变化即使生效，玩家也可能感知不强
  - 建议：与 C1 联动补“结果原因摘要”
- 风险点：五线全量同时强化会拉大实现面
  - 影响：首轮返修可能范围膨胀
  - 建议：首版先做最小可感知映射，不一次性把五线做成完整系统
- 待确认项：
  - 首版优先强化哪些“承载变化 -> 战斗反馈”映射
