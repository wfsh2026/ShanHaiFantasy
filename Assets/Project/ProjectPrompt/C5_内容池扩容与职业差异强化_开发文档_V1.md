## 6. 功能目标

- 扩充可选英雄模板和主选项池
- 拉开不同职业和不同构筑方向的差异
- 让玩家在多局中能感受到起手差异、成长差异和结果差异
- 不追求完整职业体系大扩写

## 9. 模块拆分

- 模块名称：英雄模板扩容
  - 模块类型：Mode Content
  - 模块职责：扩充不同职业和不同站位倾向的起手模板
  - 复用 / 新增 / 替换：扩充现有 `HeroPool`
- 模块名称：主选项池扩容
  - 模块类型：Mode Content
  - 模块职责：扩充不同成长线和不同 carry 落点的主选项
  - 复用 / 新增 / 替换：扩充现有 `BaseOptions`
- 模块名称：职业差异表现
  - 模块类型：Controller
  - 模块职责：让职业名、模板摘要、承载和结果摘要能形成一致表达
  - 复用 / 新增 / 替换：扩充现有 `BattleA2PanelController`

## 10. 数据流与权威状态流

- `Config`
  - 继续以内嵌内容池为首版来源，不单独新起配置资产
- `Data`
  - 英雄模板、职业字段、主选项字段都通过现有 battle 快照下发
- `Logic`
  - 服务端基于扩充后的内容池生成候选和选项
  - 服务端基于职业和承载差异生成结果摘要
- `UI`
  - 客户端只消费 battle 快照，不本地自造职业差异

## 11. Client / Server 责任分配

- 客户端负责：
  - 展示更多模板、职业信息和结果差异
- 服务端负责：
  - 生成内容候选
  - 生成 battle 结果和差异摘要
- 同步方式：
  - 继续通过 `NetworkSyncBattleStateRpc`

## 12. 关键流程

1. 开局生成更丰富的英雄候选
2. 养成阶段生成更丰富的主选项池
3. 玩家或 AI 选择后把差异写入现有 `BattleModeData`
4. 进入 `Battle / BattleResult` 时通过结果摘要反映职业与构筑差异

## 13. 对外接口与交互边界

- 继续复用现有 `BattleModeData` 与 `BattleA2PanelController`
- 不新起平行内容系统
- 不让 UI 层自行定义职业和构筑结果

## 14. 进入条件、完成出口与阻塞升级

- 进入实现前条件：
  - C1-C4 已确认仍沿现有 `BattleMode` 主链扩展
- 最小完成出口：
  - 玩家能在多局中稳定看到不同职业模板和不同成长方向
  - 结果摘要能读出至少一层职业或构筑差异
- 若扩容导致 UI 过载，优先保留内容差异，压缩文案长度

## 15. 测试与验证方案

- 测试入口：
  - `BattleTestScene`
  - `CultivationTestScene`
- 验证步骤：
  1. 连续多次进入主角选择，确认候选组合变化明显
  2. 连续多次进入养成阶段，确认主选项组合变化明显
  3. 观察 `Battle / BattleResult`，确认不同职业和构筑差异能被读出
- 最小闭环：
  - `HeroSelect -> Cultivation -> Battle -> BattleResult`

## 16. 风险与待确认项

- 风险点：一次性扩太多内容会稀释调试效率
  - 建议：首版先扩到“可明显感知差异”的数量，不追求海量
- 风险点：职业差异如果只体现在名字，玩家仍感知不到
  - 建议：必须同步进入结果摘要和 AI 倾向表达

## 17. 不做范围

- 不做完整职业树
- 不做局外收集系统
- 不做大型配置资产体系迁移
