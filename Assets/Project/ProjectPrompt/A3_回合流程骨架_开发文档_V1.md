## 5. 功能目标

- 本次开发要解决的问题：
  - 把现有“能跑但越界”的 RoundLoop stub 收口为正式 A3。
  - 建立只负责回合骨架的稳定阶段流，不提前承接 A4/A5/A6 的正式玩法。
- 产出结果：
  - 单局进入 `RoundLoop` 后，从第 1 回合 `Battle` 开始按固定顺序推进四阶段。
  - 当前回合结束后进入下一回合。
  - 开发测试链能验证至少 2 个完整回合。
- 不追求的内容：
  - 不实现正式战斗结果。
  - 不实现正式淘汰与终局。
  - 不实现正式养成与布阵内容。

## 8. 模块拆分

- 模块名称：`BattleModeData` 收口
  - 模块类型：Mode Data
  - 模块职责：只承载 A2 输出后的回合公共状态与 A3 阶段骨架状态
  - 本轮要求：
    - 保留 `mainState / roundIndex / roundPhase / participantList / matchId / sceneId / roomInviteCode`
    - 不再把 A5 的正式淘汰/终局作为 A3 的核心输出
    - 如需新增 A3 验证字段，应优先新增“权威阶段序号/阶段迁移计数/最近一次迁移信息”这类骨架字段
- 模块名称：`ServerBattleModeLogic` 收口
  - 模块类型：Mode Logic
  - 模块职责：权威推进四阶段顺序与下一回合递进
  - 本轮要求：
    - 移除或禁用当前 `Battle` 阶段直接淘汰的 stub
    - 不在 A3 内写死 `winner` 与 `GameOver`
    - 把阶段推进收口为可替换的“阶段完成门”，当前默认可由 timer 驱动
- 模块名称：`ClientBattleModeLogic`
  - 模块类型：Mode Logic
  - 模块职责：消费服务端回合快照，驱动客户端阶段展示
  - 本轮要求：
    - 不本地推断阶段顺序
    - 任何用于验收的阶段信息必须来自服务端快照
- 模块名称：`BattleA2Panel / BattleA2SceneVerifier`
  - 模块类型：Controller / Test
  - 模块职责：A3 阶段骨架验证展示
  - 本轮要求：
    - 保留 A2 显示能力
    - 扩展 `RoundLoop` 显示，至少展示当前回合、当前阶段、阶段顺序和最近阶段迁移
    - 验证 2 回合连续推进
- 模块名称：`NetworkSyncBattle`
  - 模块类型：Feature / Network Module
  - 模块职责：同步 A3 所需的权威回合骨架字段
  - 本轮要求：
    - 若当前快照字段不足以表达 A3 验收信息，再补充 Battle 快照字段
    - 不新增 UI 直连底层网络调用

## 9. 数据流与状态流

- `Config`
  - 当前版本允许继续用逻辑常量承载阶段时长
  - 本轮不强制新增配置文件
  - 但文档明确记为后续技术债，不作为长期方案
- `Data`
  - `mainState`
  - `roundIndex`
  - `roundPhase`
  - `stageName`
  - A2 输出的参与者快照与宗门环境
  - A3 新增的权威阶段迁移信息（如实现）
- `Logic`
  - 服务端进入 `RoundLoop`
  - 服务端完成四阶段顺序推进
  - 服务端在 `FormationConfirm` 完成后进入下一回合
  - 不在 A3 内生成正式战斗结果与淘汰
- `UI`
  - 展示当前回合编号
  - 展示当前阶段
  - 展示最近一次阶段迁移
  - 展示两轮连续推进验证结果

关键状态变化：

- `SectReveal -> RoundLoop`
- `RoundIndex = 1, RoundPhase = Battle`
- `Battle -> BattleResult -> Cultivation -> FormationConfirm`
- `FormationConfirm -> RoundIndex + 1 -> Battle`

## 10. Client / Server 责任分配

- 客户端负责：
  - 接收并展示回合骨架快照
  - 在验证 UI 中展示当前回合与阶段
  - 不本地生成阶段结果
- 服务端负责：
  - 维护权威回合编号与阶段编号
  - 决定阶段进入、阶段完成与回合递进
  - 广播权威 Battle 快照
- 同步边界：
  - A3 任何用于验收的计数器、迁移序号、当前阶段版本，都必须由服务端快照下发
  - 客户端 `RunningTime` 之类本地 tick 信息不作为 A3 验收依据
- 越界限制：
  - UI 不得直接操作 `NetworkSyncClient.SendCmd`
  - 业务逻辑不继续扩大对 `NetworkSyncBattleClientModule / ServerModule` 的直接依赖
  - 如需新增交互型阶段命令，必须通过 Battle 协议与 Battle 模块接入

## 11. 关键流程

1. 入口
   - A2 完成后，服务端把战局推进到 `RoundLoop`
   - 初始化第 1 回合 `Battle`
2. 回合内推进
   - 进入 `Battle`
   - 达到当前阶段完成门后进入 `BattleResult`
   - 达到当前阶段完成门后进入 `Cultivation`
   - 达到当前阶段完成门后进入 `FormationConfirm`
3. 回合结束
   - `FormationConfirm` 完成
   - `roundIndex + 1`
   - 回到下一回合 `Battle`
4. 测试验证
   - `BattleTestScene` 中持续显示当前回合与阶段
   - 至少完成 2 个完整回合

补充约束：

- 当前阶段完成门可暂时由 timer 驱动，但实现上不能把四阶段永久写死成统一 `0.2s` 自动推进。
- 应预留后续 A4/A6 接入“结果到达 / 玩家确认 / 布阵确认”的替换空间。

  - 不在 A3 中新增正式战斗/淘汰/终局结算接口

## 13. 进入条件、完成出口与回退策略

- 进入实现前必须满足：
  - A3 策划规格已固定
  - 已明确 A3 只做回合骨架
  - 已确认沿用现有 `BattleMode`、`BattleTestScene`、`BattleA2Panel`
- 最小完成出口：
  - 房间开始后，A2 完成并进入 `RoundLoop`
  - 系统从第 1 回合 `Battle` 开始
  - 四阶段稳定按固定顺序推进
  - 完成 2 个回合连续循环
  - 不提前触发正式淘汰与终局
- 回退策略：
  - 若当前 RoundLoop stub 与 A3 边界冲突，优先回退为占位逻辑，而不是保留越界逻辑继续推进
  - 若 A3 所需 UI 显示能力不足，优先扩展现有 `BattleA2Panel`，不新开 Panel 触碰 Base
  - 若新增快照字段不足，允许扩展 Battle 快照，但不改 NetworkSync 内核

## 14. 测试与验证方案

- 主验证入口：
  - `RoomEntryScene -> 开房/开始 -> BattleTestScene`
- 辅助验证入口：
  - `BattleA2SceneVerifier`
  - `BattleA2Panel`
- 验证步骤：
  1. 完成房间开始与 A2
  2. 进入 `RoundLoop`
  3. 观察第 1 回合四阶段顺序
  4. 观察进入第 2 回合
  5. 再次观察第 2 回合四阶段顺序
  6. 确认没有因为 A3 提前出现正式淘汰、胜者、终局
- 预期结果：
  - 阶段不跳段、不乱序
  - 至少 2 回合连续推进
  - 服务端快照与客户端显示一致

## 15. 风险与待确认项

- 风险 1：当前 `ServerBattleModeLogic` 已越过 A3 边界写入淘汰与终局
  - 影响：A4/A5 返工概率高
  - 处理：本轮先拆回占位逻辑
- 风险 2：当前阶段推进统一依赖 timer
  - 影响：后续接入交互型阶段时要重构
  - 处理：本轮至少把“阶段完成门”抽成清晰方法边界
- 风险 3：A3 验证字段有一部分现在仍是客户端本地推断
  - 影响：验收时无法证明权威同步正确
  - 处理：本轮新增的验收字段必须走服务端快照
- 风险 4：若新建独立 A3 Panel，会触碰 `UIManager` Base 注册点
  - 影响：超出本轮授权边界
  - 处理：本轮优先复用 `BattleA2Panel`
- 待确认项：
  - 后续是否需要把阶段默认时长收口到配置
  - 后续是否改为阶段确认制而非 timer 制
